# 032: Regex, Case-Sensitive, and Whole-Word Toggles in Find Bar

**Type:** Feature
**Priority:** P1
**Effort:** Medium
**Labels:** Editor, Search, UX
**Phase:** 1 — Foundation (MVP)

## TL;DR

The content find bar (`ContentFindBarView`) only supports plain case-insensitive substring matching. Users expect toggle buttons for regex, case-sensitive, and whole-word search — this is the #1 editing complaint from Obsidian users and table-stakes for any competent text editor.

## Current State

- `ContentFindBarView` has a search field with prev/next navigation and a match counter
- Search in `PreviewContainerViewController.searchInTextView` uses `NSString.range(of:options:.caseInsensitive)`
- No way to toggle regex, case sensitivity, or whole-word matching
- Find and replace (ticket 031) just landed but also uses plain matching

## Expected Outcome

- Three small toggle buttons in the find bar row: **Regex** (`.*`), **Case Sensitive** (`Aa`), **Whole Word** (`\b`)
- Buttons use the same icon-button style as prev/next chevrons
- Active state highlighted with theme accent color (like the outline button pattern)
- Search logic respects the active toggles:
  - **Regex**: use `NSRegularExpression` instead of `NSString.range(of:)`
  - **Case Sensitive**: toggle `.caseInsensitive` option on/off
  - **Whole Word**: wrap query in `\b...\b` word boundaries (or use `.anchored` with word boundary logic)
- Invalid regex shows a visual indicator (red border or "invalid regex" in counter label) — no crash
- Toggle state persists across searches within the session (not across app launches)
- Works in all search contexts: editor, code preview, and mmap search

## Files to Modify

- `singlepane/UI/Preview/ContentFindBarView.swift` — Add toggle buttons, expose toggle state
- `singlepane/UI/Preview/PreviewContainerViewController.swift` — Update `searchInTextView`, `searchInMmapFile`, and replace logic to respect toggle state

## Risks / Notes

- Regex search on large text views could be slow — consider debouncing or async execution
- mmap search currently uses raw byte matching — regex support there may need `NSRegularExpression` on the windowed text instead
- WKWebView search uses JavaScript — regex support there is a separate concern (could defer)
- Replace with regex capture groups (`$1`, `$2`) would be a nice follow-up but is not required for v1

## Acceptance Criteria

- [ ] Regex toggle button in find bar — active state uses regex matching
- [ ] Case-sensitive toggle button — active state uses exact case matching
- [ ] Whole-word toggle button — active state matches whole words only
- [ ] Invalid regex shows error state (no crash)
- [ ] All toggles work with find and replace
- [ ] Match counter updates correctly with all toggle combinations
- [ ] Toggle buttons styled consistently with existing find bar chrome
